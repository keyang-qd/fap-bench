# FAP-Bench: ICAIF Publication Suite

This repository contains the trimmed, publication-facing implementation of FAP-Bench for the ICAIF eight-page paper. The real-data experiment surface is intentionally limited to results that appear in the paper: method ranking, financial protocol sensitivity, common-universe partitions, controlled covariate/feature heterogeneity, matched identification controls, label-skew diagnostics, and validation-only FedAdam selection.

## What changed in this version

- FedAdam is frozen at `server_lr: 0.003`, selected only from the validation period under a validation OOS-R2 eligibility constraint.
- Validation-fitted nonnegative linear calibration is enabled for FedAdam. Both raw `fedadam` and evaluation-only `fedadam_calibrated` rows are saved.
- Legacy partition, quick, draft, duplicate calibration, and test-set hyperparameter grids were removed.
- Mild identification controls and the 5:1 size-control pair were removed from the publication run; the stronger 20:1 and temporal controls remain.
- Non-core grids train only methods used in the paper figures. Local and FedProx remain in the headline FF12 table but are not repeatedly trained in every stress test.
- Resume is configuration-safe: an existing run is reused only when its `resolved_config.json` matches the requested data, method, partition, seed, and hyperparameters. Old FedAdam-0.01 outputs cannot be silently reused.
- One command now runs all experiments, audits them, and creates merged results, paper tables, figures, and a Markdown report.

> **Panel path.** CRSP--Compustat is licensed and cannot be distributed, so every
> shipped config carries the placeholder `/path/to/qdata/...`. Point runs at your
> own built panel with `--data-path` (`run_grid.py` and
> `run_publication_experiments.py` both accept it) rather than editing the YAML.
> Resume compares the *resolved absolute* path, so reruns must pass the same
> value to reuse completed cells. To try the pipeline without any licensed data,
> use `python scripts/run_benchmark.py --config configs/synthetic_smoke.yaml`.


The revised CRSP--Compustat recipe in `scripts/data_recipe2_revised.py` produces one row at formation month `t` and a strictly aligned delisting-adjusted target return in month `t+1`.

The main configuration expects:

```yaml
data:
  date_col: formation_date
  target_col: retadj_1mn
  target_shift_months: 0
  target_date_col: target_date
split:
  date_col: target_date
  train_end: 2014-12-31
  val_end: 2018-12-31
evaluation:
  date_col: target_date
```

Do not change `target_shift_months` to 1 for data generated by the revised recipe.

## Run every paper experiment with one command

The data path in the base YAML is the author's local path. The safest invocation overrides it explicitly:

```bash
caffeinate -i python -u scripts/run_publication_experiments.py \
  --data-path /path/to/qdata/data0712.parquet
```

This one command now covers every phase, **including the expanded-features
robustness check**: if `core_expanded_features` needs to run and
`data0712_expanded.parquet` does not already exist at `--expanded-data-path`
(default: alongside `--raw-data-dir`, default `/path/to/qdata`), it is
built automatically before that phase trains (`data_recipe2(...,
include_expanded_characteristics=True)`, ~30 minutes, one-time — pass
`--rebuild-expanded-panel` to force a rebuild). `--data-path` never touches
`core_expanded_features`'s own data path, since that phase trains on a
different (20-characteristic) panel; use `--expanded-data-path` if you need
to override it specifically.

The command sequentially runs all phases and safely resumes completed cells:

| Phase | Scenarios | Trained methods |
|---|---|---|
| `fedadam_validation` | server LR 0.001, 0.003, 0.01, 0.03 | FedAdam only |
| `core` | full participation, 50% participation, 10×5 local steps, price > $5, microcap exclusion | Centralized, Local, FedAvg, FedProx, SCAFFOLD, FedAdam |
| `partitions` | FF12, IID-12, exchange, size quintile, SIC-major-group (up to 30 clients) on one common universe | Centralized, FedAvg, SCAFFOLD, FedAdam |
| `heterogeneity` | covariate mild/strong; feature mild/moderate/severe; matched controls for each of the five (`*_matched`) | Centralized, masked centralized where applicable, FedAvg, SCAFFOLD, FedAdam |
| `identification` | 20:1 size imbalance and matched retention; persistent/block timing and matched-random schedules | FedAvg, SCAFFOLD, FedAdam |
| `label_diagnostics` | mild and strong controlled label skew | diagnostics only; no model training |
| `core_expanded_features` | same five scenarios as `core`, on the 20-characteristic panel (7 profitability + 13 value/investment/financing/accrual/intangible/size/momentum, see `EXPANDED_CHARACTERISTIC_COMPONENTS` in `scripts/data_recipe2_revised.py`) | Centralized, Local, FedAvg, FedProx, SCAFFOLD, FedAdam |

The default plan contains 475 scenario-seed cells: 465 training cells and 10 diagnostics-only cells. `fedadam_validation`, `label_diagnostics`, and `partitions` use seeds `[11, 22, 33, 44, 55]` (5 seeds). `core` and `core_expanded_features` extend the same `i*11` pattern to 10 seeds. `identification` and `heterogeneity` extend it to 20 seeds: `core` and `identification` because those two phases underlie the paper's most statistically fragile claims (Table 1 method rankings and the matched-control contrasts in Figure panel (d)); `core_expanded_features` because per-seed Sharpe on the 20-characteristic panel is noisy enough that 5 seeds could not support a confident robustness claim; `heterogeneity` because it now also carries matched-control comparisons (`*_matched` scenarios, see "Statistical significance outputs" below), and matched-control contrasts are exactly the case `identification`'s own seed increase was motivated by — see `EXPERIMENT_ENHANCEMENT_PLAN.md` and `MANUSCRIPT_REVISION_PLAN.md` in the paper repository for the rationale.

## FedAdam selection rule

The validation phase selects the highest mean validation Rank IC among candidates satisfying:

```text
mean validation_selected_oos_r2_zero >= -0.05
```

The publication plan expects the selected value to be exactly `0.003`. The all-in-one runner stops before the main paper results if validation selection no longer supports that frozen value. This prevents accidental publication with a hyperparameter chosen from test performance.

## Identification safeguards

Before paper outputs are built, the runner verifies:

- all partition scenarios use the same row fingerprint and row count;
- the size-quintile partition produces exactly five clients;
- size imbalance and its uniform-retention control differ in training rows by no more than 2%;
- structured and matched-random temporal scenarios have identical active-client counts per round;
- structured and matched-random temporal scenarios have identical total participation for every client;
- each covariate-shift matched control (`covariate_shift_*_matched`) applies exactly one
  `(location_shift, scale_multiplier)` pair per feature across all clients (`fapbench.audit.
  validate_heterogeneity_matched_controls`);
- each feature-heterogeneity matched control (`feature_heterogeneity_*_matched`) has
  `feature_jaccard_dissimilarity == 0.0` (every client sees the identical feature set).

The last two checks are exact, not tolerance-based like the size-imbalance check above: the matched
controls collapse the treatment's realized per-client draws to one shared value applied identically
to every client, so there should be zero cross-client variation at all, not an approximate match.

Any failed audit stops the publication build.

## Statistical significance outputs

`build_publication_outputs` (in `fapbench/publication.py`) also runs the
paired HAC return test and moving-block-bootstrap Sharpe interval already
implemented in `fapbench/evaluation/statistics.py`, via the aggregation
helpers in `fapbench/evaluation/significance.py`:

- `paper_tables/main_results_significance.csv`: for the reference scenario
  (`REFERENCE_SCENARIO` in `fapbench/publication.py`, currently
  `ff12_exclude_microcaps` — the *investable* universe; see "Reference protocol"
  below), each non-centralized method's client-neutral net-return series is
  tested against Centralized's within every completed seed directory using the
  Newey-West HAC test, then the per-seed p-values are combined with Stouffer's
  method.
- `paper_tables/main_results_sharpe_intervals.csv`: per-method moving-block-bootstrap
  Sharpe confidence intervals, averaged across seeds.
- `paper_tables/identification_hac_tests.csv`: for each matched-control pair in
  `IDENTIFICATION_PAIRS`, the treatment-minus-control monthly net-return
  difference is tested for a zero mean within every seed, then combined.
- `paper_tables/heterogeneity_dispersion_hac_tests.csv`: for each scenario in
  `HETEROGENEITY_DISPERSION_SCENARIOS`, the treatment-minus-`core`-reference
  monthly *cross-client* Rank-IC dispersion (std across clients, and the
  worst single client) is tested for a zero mean within every seed, then
  combined. This complements `identification_hac_tests.csv` and the
  heterogeneity paragraph's point estimates: `covariate_shift`/
  `feature_heterogeneity` perturb each client with an independently, randomly
  signed shift (see `build_covariate_shift_parameters` in
  `fapbench/partition/statistical.py`), so a mean-based test on the
  client-neutral net-return series can cancel out even when the treatment
  clearly widens the spread across clients; testing dispersion directly
  avoids that cancellation.
- `paper_tables/heterogeneity_matched_control_hac_tests.csv` and
  `paper_tables/heterogeneity_matched_control_dispersion_hac_tests.csv`: for each pair in
  `HETEROGENEITY_MATCHED_CONTROL_PAIRS` (`covariate_shift_mild/strong` and
  `feature_heterogeneity_mild/moderate/severe`, each against its own `*_matched` scenario), the same
  mean-return and dispersion tests as above, but against a matched control instead of the plain `core`
  reference. This closes an asymmetry: `size_imbalance_ratio_20_identified` and the two
  `temporal_*_identified` scenarios (`IDENTIFICATION_PAIRS`) already had a matched control holding a
  specific confound (data volume, participation) fixed while varying only the structural pattern;
  `covariate_shift`/`feature_heterogeneity` did not, even though they admit natural matched-control
  constructions (`build_covariate_shift_matched_control_parameters` collapses the treatment's
  per-client shifts to one shared value via the arithmetic/geometric mean of the realized draws;
  `build_feature_masks_matched_control` draws the private feature subset once and shares it across
  every client instead of drawing independently per client, both in `fapbench/partition/`). Methods are
  auto-detected per pair from each pair's own `benchmark_results.csv` rather than hardcoded, since a
  treatment and its own matched control always report the same method set.
- `paper_tables/identification_dispersion_hac_tests.csv`: the same dispersion test applied to
  `IDENTIFICATION_PAIRS`, completing the symmetry in the other direction.
  `identification_hac_tests.csv` tests the *mean* client-neutral net-return series for those pairs;
  this tests cross-client *spread* for them. With both files present, all eight heterogeneity
  treatments the benchmark reports (3 system-level + 5 data-level) are measured on one metric against
  one kind of control. The system-level dispersion effects are roughly an order of magnitude smaller
  than the data-level ones.
- `paper_tables/matched_control_dispersion_monthly.csv`: **the primary inference for the paper's
  matched-control claims**, and what Figure 2(c) plots. The Stouffer-combined tables above treat each
  seed as a test and combine across them; training seeds share one realized market history and differ
  only in optimization-path noise, so that combination understates the true tail probability by a wide
  margin (it produced p-values around 1e-70). `seed_averaged_dispersion_contrasts`
  (`fapbench/evaluation/significance.py`) instead takes the **calendar month** as the unit of
  inference: the treatment-minus-control monthly series is averaged across seeds into one ~60-month
  series, then tested with Newey--West HAC plus a moving-block bootstrap interval
  (`moving_block_bootstrap_mean`), under Benjamini--Hochberg FDR control across the whole reported
  family (`benjamini_hochberg`, both in `fapbench/evaluation/statistics.py`). Averaging preserves the
  mean, so **effect sizes are identical** to the per-seed tables; only the uncertainty statement
  changes. `seed_sign_agreement` is descriptive and carries no independence claim. The
  Stouffer tables are retained for comparison but should not be cited as the paper's evidence.

### Reference protocol

The headline protocol is `ff12_exclude_microcaps` — the **investable** universe — set by
`REFERENCE_SCENARIO` in `fapbench/publication.py`. It is not the unrestricted universe, because most
of the unrestricted universe's apparent predictability sits in the microcap segment: Centralized Rank
IC is `0.0452` there against `0.0111` once microcaps are dropped, and every client-neutral net Sharpe
flips sign. Reporting the unrestricted number as the headline would overstate what these methods
deliver on tradeable stocks, so it is reported as a sensitivity instead
(`main_results_unrestricted.csv`, and the `ff12_full_participation` rows of `protocol_sensitivity`).

Two things deliberately do **not** follow this constant, and changing them would be a bug:

- `_heterogeneity_table` and `_expanded_features_table` stay on `UNRESTRICTED_SCENARIO`, because the
  heterogeneity and expanded-panel grids were themselves run on the unrestricted universe. Their
  reference arm has to match the arm they are differenced against, or the comparison would vary the
  universe and the treatment at once.
- `REFERENCE_SCENARIO` in `fapbench/robustness.py` is a separate constant and stays unrestricted, for
  the same reason: every robustness variant (`wide_mlp`, `linear_ridge_*`, `fedprox_mu_*`,
  `cost_*bps`, `local_tuned`) was run on the unrestricted universe. Only
  `ranking_disagreement_test`, which is a property of the reference protocol itself rather than a
  difference against it, is run on both and reports one row per universe.

Because RQ3 therefore measures heterogeneity on a different universe from Table 3, its levels are not
comparable with the headline table; the manuscript states this rather than leaving it implicit.

### Robustness grid

`configs/icaif_robustness.yaml` (10 scenarios x 10 seeds) answers five reviewer questions against the
unrestricted-universe reference (`core/ff12_full_participation`), all reachable by configuration:

| Scenarios | Question |
|---|---|
| `linear_ridge_weak`, `linear_ridge_strong` | Is the MLP the right base learner? (`model.hidden_dims: []` reduces it to linear regression; `weight_decay` is the ridge penalty) |
| `wide_mlp` | Do method rankings depend on capacity? (`[256,128]`, ~35k params vs ~2.6k) |
| `fedprox_mu_*` | Is FedProx distinguishable from FedAvg at any mu? |
| `cost_25bps`, `cost_50bps` | Do economic results survive realistic transaction costs? |
| `local_tuned` | Is the local-only baseline undertuned? |

That last one needed code, not just config: local models otherwise inherit the federated client
hyperparameters verbatim, so "federation helps" was partly a statement about the budget-matching
protocol. `baselines.local_tuning` (`_local_tuning_grid` in `fapbench/runner.py`) sweeps a
learning-rate x weight-decay grid, trains all clients per candidate, keeps per client the candidate
with the best validation Rank IC, and writes the selections to `local_selected_hyperparameters.csv`.
It is **off by default**, so existing results are byte-identical, and it raises if enabled without
`model_selection.enabled` — without per-client validation there is no signal to select on and the
sweep would silently keep whichever candidate ran first.

`fapbench/robustness.py` aggregates the grid into four seed-paired tables
(`robustness_model_class`, `robustness_fedprox_mu`, `robustness_transaction_costs`,
`robustness_local_tuning`) and is called automatically by `run_publication_experiments.py`; the tables
are empty until the grid has been run. Note these four use **across-seed paired t-tests**: they are
within-seed paired contrasts under the one market history, so the estimand is "does this protocol
change move the metric, over the seed draw". That is a different question from the matched-control
contrasts, whose unit of inference is the calendar month — do not compare the two sets of p-values.

`market_adjusted_alpha` adds a fifth table, `robustness_market_adjusted_alpha`. It regresses each
method's seed-averaged monthly client-neutral net return on an equal-weighted proxy for the panel's
own market return, using `newey_west_ols` (Bartlett kernel, automatic bandwidth, matching
`newey_west_mean_test`), and reports beta, alpha, and their HAC p-values. This bounds the "is the
reported performance just market exposure?" objection; it is **not** a full factor model, since the
proxy is the equal-weighted own-universe return rather than a value-weighted market or FF5+momentum
set. It needs the panel itself, so it takes a `panel_path` argument and returns an empty frame when
that is None or missing — the publication build stays runnable without the licensed data.

`robustness_metric_rank_agreement` is a sixth table and exists to defend RQ1. Because the linear
model beats the reference MLP outright, a reader can reasonably ask whether RQ1's metric-disagreement
finding is an artifact of a badly-chosen architecture. The table reports, per model class, the
Spearman correlation between mean Rank IC and mean net Sharpe across methods and whether one method
tops both. It does not, at any of the three classes — so the disagreement is a property of the
evaluation rather than of the architecture, while *which* method wins is not.

`capacity_separation_contrasts` is a seventh table, `robustness_capacity_separation`, fed by the
separate `configs/icaif_capacity_separation.yaml` grid. It answers the objection that RQ3's
data-level/system-level separation might be a statement about model capacity: if a 2,625-parameter
network converges to nearly the same point regardless of update schedule, the small system-level
footprint would be an artifact of the model rather than a finding about federated learning. Note the
`wide_mlp` scenario does **not** answer this — that widens the model under the *reference* protocol,
so it shows whether method rankings move with capacity, not whether the matched-control separation
does. Answering it requires re-running matched-control *pairs* at higher capacity, which is what this
grid does for three pairs (two data-level, one system-level) at `[256, 128]` (~35k parameters). It
reuses `seed_averaged_dispersion_contrasts` unchanged, so the effects are directly comparable to the
reference-capacity ones in `matched_control_dispersion_monthly`. Like the other separately-run grids,
the table is written empty until the grid exists.

Three further tables answer the same "is the separation real?" question at other settings, all fed by
separately-run grids and all built from the same `_phase_dispersion_contrasts` helper so their effects
stay comparable with `matched_control_dispersion_monthly` cell for cell:

| table | grid | question |
| --- | --- | --- |
| `rq3_investable` | `configs/icaif_rq3_investable.yaml` | does the separation survive the *reference* universe? The heterogeneity grid ran unrestricted, so RQ3's headline was measured on a universe the paper does not use as its reference. |
| `linear_separation` | `configs/icaif_linear_separation.yaml` | does it survive the model class RQ2 identifies as the sharpest lever? |
| `severity_escalation` | `configs/icaif_severity_escalation.yaml` | the two heterogeneity families are dialled in incommensurable units, so nothing establishes that "severe" masking and a 40% outage block sit at comparable severities. Rather than assert calibration, escalate: outages 40% -> 60% -> 80%, imbalance r=20 -> 50 -> 100, each rung with its own matched control, and report where the system-level effects land. |

These are named without the `robustness_` prefix because the manuscript cites them as RQ3 results
rather than appendix material, and `scripts/audit_manuscript_numbers.py` in the paper repository binds
these exact filenames.

### Ensemble of local models

`baselines.ensemble_local` (default **off**) adds an `ensemble_local` method row.
Federation is not the only way to use K clients' data without pooling it: the cheap
alternative is to train locally, ship the K finished models once, and average their
opinions -- no rounds, no coordination, no shared optimizer state. If that matched
federated training, the benchmark's central comparison would be far less
interesting, so it is measured rather than argued away.

Two implementation choices matter and are pinned by `tests/test_ensemble_local.py`:

- **Ranks are averaged, not scores.** Independently trained local models are not
  calibrated against each other -- the same reason the local-only *portfolio* score
  is a within-client percentile rank. Averaging raw scores would let one member's
  scale decide the ensemble; averaging within-month cross-sectional percentile ranks
  makes the result invariant to any monotone rescaling of an individual member.
- **Each member scores under its own feature mask.** A client that never saw a
  characteristic does not get it back at inference, so an ensemble member is the
  model as it was actually trained.

Because rank-averaging discards level information, the ensemble's prediction is a
percentile rather than a return, so every squared-error metric (`mse`, `mae`,
`oos_r2_*`, and their per-client variants) is written as `NaN` for this row and
`prediction_scale` records why -- an OOS \(R^2\) of -20 against realized returns is a
category error, not a poor result. Rank IC, the portfolio metrics, and the
client-level metrics are all well defined and are reported normally.

The baseline requires `baselines.local`, and asks for it explicitly: the ensemble
aggregates the local baseline's own per-client models, so the two rows decompose one
training run into training and aggregation. A config requesting the ensemble without
the local baseline raises rather than silently skipping. `configs/icaif_ensemble_local.yaml`
runs it on both the reference and unrestricted universes at the same 10 seeds as
`icaif_core.yaml`, with every other method trained in the same run so the contrasts
are exactly paired.

### Client-local standardization

The panel's characteristics are standardized by a within-month rank-then-z-score over the **full**
cross-section, computed at panel construction, before clients exist. That is look-ahead-safe but
global across clients, which sits awkwardly against the premise that raw data cannot be pooled: no
client in the stated deployment could compute it. Because RQ3's dependent variable *is* cross-client
dispersion, this is not a footnote -- a step that equalizes clients' feature distributions is a
candidate explanation for RQ3's own headline.

`data.client_local_standardization: true` (see `client_local_rank_zscore` in `fapbench/data.py`)
re-standardizes each feature within `(client, month)` instead. It runs **after** client assignment and
**before** the train/val/test split, so every split sees the same transform. It is **off by default**,
so previously published results are byte-identical.

Two properties make it a genuine client-local statistic rather than a re-scaling of a pooled one:

- Ranking is invariant to monotone transforms, and every upstream step (the panel's global rank
  z-score, then `PanelPreprocessor`'s affine train-statistic scaling) is monotone within a month. So
  re-ranking inside a client gives exactly what ranking the raw characteristics inside that client
  would have given -- `test_client_local_rank_zscore_is_invariant_to_monotone_upstream_steps` asserts
  this to 1e-12.
- It uses only the client's own contemporaneous cross-section, so it is look-ahead-safe on the same
  terms as the global version.

A client-month with fewer than two usable observations has no cross-section to rank and is set to
`0.0` rather than dropped, so client sample sizes are unchanged and the size-imbalance treatments stay
comparable.

`configs/icaif_client_local_standardization.yaml` re-runs the largest data-level contrast (severe
feature heterogeneity and its matched control) under this setting; 20 cells.

### Expanding-window rolling refits

`scripts/make_rolling_config.py` generates `configs/icaif_rolling_refit.yaml`: one scenario per test
year, training through Y-5, validating on Y-4..Y-1, and predicting Y. Rolling Y over 1990-2023 gives
34 windows and ~408 out-of-sample months against the single-window protocol's 60. The point is
statistical power, not realism alone: at n=60 no method's net Sharpe separates from Centralized and
every headline interval contains zero, and seeds cannot fix that because they share one market
history.

Rolling is expressed as a **grid of scenarios, not a new training loop** -- `split.test_end` (added to
`split_by_time`) caps each window's test set to one step, so every window is an ordinary run and
reuses partitioning, budget matching, checkpoint selection, and resumability unchanged.
`fapbench/rolling.py` then concatenates the per-window monthly series. That is valid because
portfolios are formed within each month, so adjacent windows join without overlap -- and
`_concatenate` raises rather than silently averaging if two windows ever cover the same month, which
would mean overlapping test sets and reused observations.

Regenerate the config after changing the schedule; do not hand-edit the YAML. `--step 2` halves the
cost by refitting biennially.

`configs/icaif_capacity_separation.yaml` and `configs/icaif_linear_separation.yaml` (6 scenarios x
10 seeds each) are the same defence applied to RQ3, which the tables above do not cover: the
heterogeneity and identification grids only ever ran at `[64,32]`. Running both measures the
matched-control separation at 8, 2,625, and 35,073 parameters. Their scenario blocks are byte-identical
to each other by construction — only `model.hidden_dims` and the ridge penalty differ — so the
contrasts stay comparable across model classes; if you edit a treatment in one, edit all three files
together. The capacity config answers a question `wide_mlp` does **not**: whether the
data-level/system-level *separation* survives higher capacity.
It re-runs three matched-control pairs at `[256,128]` — feature-severe, covariate-strong, and block
outages — so the contrasts themselves can be re-measured. Its treatment parameters are diffed against
`icaif_heterogeneity.yaml` and `icaif_identification.yaml`; if you edit either, re-check that they
still match, since a silent drift would look like a capacity effect.

These use the ~60-month test-period time series within each seed as a second,
complementary source of statistical power to the cross-seed mean/std already
reported in `identification_contrasts.csv` and the main results table, which
only has as many independent points as there are seeds. Seeds are not fully
independent draws (they share the same realized market history and differ
only in training-path noise), so treat the combined p-values as a measure of
cross-seed directional consistency, not an exact test with independent
samples. All seven tables require the raw per-seed `benchmark_results.csv`,
`portfolio_returns_*.csv`, and (for the three `*_dispersion_hac_tests.csv` files only)
`predictions_*.parquet` files to still
be present under `outputs/icaif_publication/<phase>/<scenario>/seed_<seed>/`; if a run directory was
cleaned up after aggregation, that scenario's row is silently omitted rather than failing the whole
build.

## Laptop and server execution

The included grids use the conservative Apple-silicon setting:

```yaml
grid_execution:
  parallel_runs: 1
  max_total_client_workers: 4
  max_total_torch_threads: 4
```

Run only one publication command at a time. On a high-memory machine, `parallel_runs` can be increased to 2 together with the worker and thread budgets, but each process loads its own full panel.

Long sequential grids explicitly close each per-run log handler after completion. This prevents macOS `OSError: [Errno 24] Too many open files` failures when later client worker pools are spawned. After an interrupted publication run, rerun the same command: `resume_completed: true` reuses completed seed directories and starts again from the first incomplete run.

## Expanded-characteristics robustness check (Tier 2)

`data_recipe2` in `scripts/data_recipe2_revised.py` defaults to the original
7-characteristic profitability panel. Passing
`include_expanded_characteristics=True` additionally computes 13 more
characteristics (`EXPANDED_CHARACTERISTIC_COMPONENTS`), bringing the panel to
20 total -- the target set in `EXPERIMENT_ENHANCEMENT_PLAN.md` Tier 2 needed
to justify "high-dimensional" language in the paper's motivation:

- value: `bm` (book-to-market, `be / me`), `ep` (earnings yield, `ib / me`),
  `cfp` (cash-flow yield, `(ib + dp) / me`), `sp` (sales-to-price,
  `sale / me`), `dy` (dividend yield, `dvt / me`),
- investment: `agr` (asset growth: prior-fiscal-year-over-fiscal-year change
  in `at`), `capx_at` (capital investment intensity, `capx / at`),
- financing: `lev` (book leverage, `lt / at`),
- accruals: `acc_at` (Sloan-1996-style accruals-to-assets),
- intangible investment: `rdoa` (R&D intensity, `xrd / at`; a missing `xrd`
  is treated as zero R&D reported, not genuinely missing, unlike every other
  ratio here which is industry/global-median imputed),
- size: `logme` (`log1p(me)`),
- momentum: `mom_2_12` (12-2 skip-month momentum: cumulative return over the
  exact-calendar-month window `[t-12, t-2]`, NaN if any intervening month is
  missing) and `mom_1_1` (prior 1-month return / short-term reversal, the
  formation month's own realized return),

each with its own cross-sectional rank z-score, following the same
imputation and never-forward-fill-returns conventions as the original seven.
Two new raw Compustat fields (`dvt`, `xrd`) are required only on this path,
so the default 7-characteristic path is unaffected.
`configs/icaif_core_expanded_features.yaml` (10 seeds, matching `core`; same
five `core` scenarios, pointed at `crsp_compustat_profitability_expanded.yaml`) checks
whether RQ1's qualitative findings replicate with a richer 20-characteristic
input space; the MLP architecture is deliberately held fixed rather than
re-tuned for the wider input, so the feature set is the only treatment
variable. It is registered as the `core_expanded_features` phase in
`configs/icaif_publication.yaml`, so `run_publication_experiments.py` builds
the expanded panel automatically and runs it as part of the single command
described above -- no separate step is needed. The original panel and
`configs/icaif_core.yaml` are unaffected; `include_expanded_characteristics`
defaults to `False`.

To build or inspect the expanded panel on its own (e.g. for debugging,
without running the grid), use `scripts/build_expanded_panel.py` directly:

```bash
python scripts/build_expanded_panel.py \
  --input-path /path/to/qdata \
  --output-path /path/to/qdata/data0712_expanded.parquet
```

`build_publication_outputs` also adds a `feature_set` comparison table,
`paper_tables/expanded_features_comparison.csv` and
`paper_figures/expanded_features_rank_ic.png`, contrasting the
`ff12_full_participation` scenario's Rank IC / OOS R2 / net Sharpe under the
7- vs. 20-characteristic panels, whenever `core_expanded_features` was
included in the run.
